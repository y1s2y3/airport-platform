# 任务单执行人回复

入口：调度中心 → 任务单（`#/coc-admin/notice`）；办理入口：工作台 → 我的待办，个人中心共用同一组待办与已办。任务单标题旁提供“原型提示：处理页面进入【工作台】-【我的待办】查看，快速入口”。依据用户提供的“任务单或签回复迭代 v1.4”HTML、详情截图及文字规则实施。用户已确认旧“已下发／已接收”没有有效回复时迁移为“处理中”，并保持提示函、处罚单流程独立。

## 实体与字段来源

| 对象 | 唯一标识与归属 | 本轮处理 |
| --- | --- | --- |
| 任务单 | 原任务单 `id`；`coc-admin-dispatch-notices` | 唯一业务记录，保留原项目、工作要求、来源、时限、备注、附件及历史字段 |
| 执行人 | 系统用户管理的用户 ID | `executors` 保存展示名称，`executorAssignments` 只保存账号引用和名称快照，不复制用户实体 |
| 有效回复 | 任务单内 `reply`，最多一份 | 保存处理人、处理人账号、处理时间、结果、说明及处理图片 |
| 我的待办／已办 | 由任务单与用户账号派生 | 仅流程投影，刷新从任务单恢复，不单独维护第二份回复 |

基本信息来自原填报字段。`createdBy/createdAt`（创建人／时间）、`issuedBy/issueTime`（下发人／时间）、`voidedBy/voidedAt`（作废人／时间）由对应操作自动记录。`reply.actor/actorUserId/time/result/remark/attachments` 分别来自实际处理用户、系统提交时间及处理表单。`closedTime` 与回复时间相同，`closedBy` 为“系统”。

当前 Web 登录账号优先与启用的系统用户关联，和平台顶栏身份保持一致；无 Web 会话时使用既有原型身份。账号 ID 决定待办与已办归属，不能通过修改处理表单指定其他处理人或处理时间。旧执行人名称仅在唯一匹配时关联账号；同名歧义不猜测账号。

## 状态与操作

| 状态 | 业务含义 | 允许操作及后续状态 |
| --- | --- | --- |
| 待下发 | 已创建，尚未下发 | 编辑、确认下发、作废、详情；确认下发后进入“处理中” |
| 处理中 | 已下发，等待执行人回复 | 台账仅详情；指定执行人通过我的待办提交处理 |
| 已完成 | 一名执行人成功提交“已执行” | 只读详情及处理记录 |
| 无需执行 | 一名执行人成功提交“无需执行” | 只读详情，流程结束 |
| 已作废 | 下发前取消任务 | 只读详情，流程终止 |

新增、编辑支持多选启用的系统用户。旧记录中的执行人继续回显；新任务可选人员来自系统用户管理。任务单的状态定义单独维护，提示函继续沿用原“待下发／已下发／已接收／已作废”规则。

## 我的待办与一次有效回复

- 下发后向每位执行人生成一条“待处理”的任务单待办，业务类型为“处理”。个人中心按当前用户账号筛选任务单待办。
- 处理页分“任务信息”“任务处理”“处理流程”。处理结果必选“已执行”或“无需执行”；处理说明对两种结果均必填；附件沿用既有图片组件，允许 0～9 张，单张上限沿用平台图片档位（合并团队 2026-11-11 更新后为 15MB）。处理时间不可编辑，提交成功时记录 `YYYY-MM-DD HH:mm:ss`。
- 提交时重新读取任务单并校验指定执行人、处理中状态及尚无有效回复。支持 Web Locks 的浏览器中，所有任务单回复在同源锁内串行写入，避免两个标签页相互覆盖；锁内仍再次校验最新记录。
- 首次成功回复后，原任务单立即进入“已完成”或“无需执行”，回复和流程结束使用同一个时间。删除该任务全部执行人的待办，只向实际处理人的“我的已办”投影一条“已完成”记录。
- 其他执行人不会得到这条已办，不能通过已办链接访问处理用户的记录。其已打开的待办在同步后失效并返回列表；迟到或重复提交不会覆盖首次回复。
- 写入本地存储失败时不得显示处理成功；处理页保留填写内容，允许重试。刷新后从原回复恢复已办，不重复追加。

## 详情与处理流程

台账详情和个人中心复用 `DispatchTaskDetailPanels.vue`，保持字段与流程一致。台账详情分“基本信息”“任务处理详情”“处理流程”。处理详情展示处理人、处理时间、处理结果、处理说明及处理附件；未回复时展示对应等待信息。

| 当前状态 | 处理流程节点 |
| --- | --- |
| 待下发 | 创建任务单（已完成）→ 下发任务单（待进行） |
| 处理中 | 创建任务单 → 下发任务单 → 执行人回复（待进行） |
| 已完成 | 创建任务单 → 下发任务单 → 执行人回复（已执行）→ 流程结束 |
| 无需执行 | 创建任务单 → 下发任务单 → 执行人回复（无需执行）→ 流程结束 |
| 已作废 | 创建任务单 → 作废任务单（终止） |

创建节点取创建人和创建时间；下发节点取实际下发人、下发时间及执行人；回复节点取实际回复者、回复时间和处理结果；结束节点为系统，时间与回复时间相同。作废节点只取实际作废人和作废时间，不套用正常回复结束节点。旧记录缺少创建、作废元数据时显示 `--`，不补造时间或用登记人冒充作废人；旧签收时间只作为历史信息展示。

视觉调整限定在任务单：详情三个区块统一使用 32px 间距，标题与内容统一留白，处理说明独占一行，长文本自动换行。弹窗标题固定，正文独立滚动；新增／编辑的底部操作固定。详情宽度上限为 1000px，并限制在可用视口内；局部滚动条使用细样式。保留平台颜色、字体、表格与既有图片查看方式，不改其他模块弹窗。

## 旧数据与示例

升级前将原任务单存储备份到本地 `coc-admin-notice-before-reply-v1`。旧“已下发／已接收／已闭环／待签收”没有有效处理回复时转为“处理中”，保留原签收信息，不生成已完成回复。已有有效回复按实际结果恢复终态。

一次性补充五种状态的 `GZ-REPLY-DEMO-*` 示例，名称和备注明确标识“示例”；新示例不覆盖同编号记录，也不删除原任务。升级标志为 `coc-admin-notice-reply-v1`，刷新不会重复生成。业务仍为浏览器本地 Mock，没有新增后端服务或真实业务接口。

按用户 2026-11-11 确认的演示方式，每个启用账号首次进入任务单或工作台时，检查本账号是否已有“处理中”“已执行”“无需执行”示例；缺少的分支补充独立任务单示例。已办示例的回复人绑定本账号，不改其他账号已有回复，不改原有手工数据；已办列表将本账号的任务单示例稳定排在前面。按账号保存一次性标志 `coc-admin-notice-personal-examples-v1:<用户ID>`，刷新不重复增加，处理过的示例不会恢复为待办。

快速入口跳到 `#/workbench?tab=todo&focus=dispatch-task`，选中“我的待办”，清空遗留筛选，在当前账号完整待办列表中优先查找可处理的任务单示例，没有示例时查找其他可处理任务单。按记录实际位置及每页条数计算页码，高亮并滚动到该行；不通过筛选缩减列表来固定显示第一页。定位完成后，用户仍可正常筛选、翻页和切换页签；没有待处理任务单时提示当前账号暂无待处理任务单。
